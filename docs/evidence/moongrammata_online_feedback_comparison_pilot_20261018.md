# Synchronous online-feedback comparison: two small pilots (2026-10-18)

## Question and protocol

This pilot checks that the pinned MoonGrammata `Target` callback consumes
results from the differential verifier synchronously while its campaign is
running, and that the harness can retain comparable per-arm outcomes. It is a
plumbing-and-exploration run, not a claim that MoonGrammata is more effective.

Each cohort uses one freshly generated, non-overlapping eight-seed MoonSmith
candidate pool, depth 4, JS/Wasm/Wasm-GC, a 30-second per-target timeout, and
three candidate slots per arm (nine expected backend attempts per arm).
Sequential and semantic-guided controls select from the frozen pool and then
use the same verifier. The semantic-guided policy is greedy inverse-pool-
frequency reference-path novelty constrained by the sequential arm's source-
size-quartile counts. MoonGrammata receives a synchronous verifier response
for each target callback while selecting identifiers from that same pool.
All arms share each cohort's pool and harness; MoonGrammata campaign seeds are
separate from the pool seed ranges.

The pool is generated by a prescreen step shared by the arms. That prescreen
uses MoonSmith reference-interpreter path labels; it is not backend runtime
coverage. Therefore this is a matched case/backend-execution-count pilot, not
an equal-wall-clock stopping-budget experiment. Prescreen and campaign costs
are kept visible. Durations are descriptive only: arms ran sequentially on one
workstation, warm caches/process startup affect them, and no throughput ranking
is justified. The semantic-guided control is also offline with respect to
selection feedback; only its selected cases are verified live.

The verifier records generation, reference evaluation, reference trace,
backend build/execution, and residual verifier time. The phase durations are
wall-clock subprocess measurements and their categories include startup; they
are not compiler-only timings. Backend statuses and all per-callback records
are retained in JSON. The outer campaign wall time is reported separately.

Both pools passed the harness start/end digest check. In each three-case pilot,
the online campaign returned three callbacks and selected three distinct seeds;
all nine requested backends ran successfully. The observed path counts were
slightly lower for MoonGrammata than either control in both pools (40 vs. 41,
then 41 vs. 44). This is only a repeated descriptive pattern across two tiny
pools, not statistical evidence or a general result. No backend mismatch or
crash was observed. These cases consequently say nothing about bug-finding
yield, backend coverage, or rare failures.

These small sequential runs do not control order effects, process/cache state,
or equal total elapsed-time budgets. They must not be read as a speed
comparison.

## Limits and next experiment

This advances the prototype from a live-target smoke test to a retained,
three-arm comparison harness with synchronous feedback and timing breakdowns.
It does **not** yet provide a fair effectiveness conclusion: each pool has
only eight proposals and each arm checks only three. The controls still select
from reference-path-prescreened cached metadata, unlike the online MoonGrammata
callback, and total wall-clock stopping budgets are not equal. A stronger
experiment should preregister many independent seed pools and campaign seeds,
include genuine live sequential and explicitly defined live semantic-guided
control arms, normalize total verifier cost or stop on a common wall-clock
budget, and report path novelty, backend divergences/crashes, verifier costs,
and all failed/timed-out cases. Any result must keep reference-path diversity
separate from backend coverage.

No new MoonBit compiler bug is claimed. Upstream issues #1322 and #2228 remain
external reports; this pilot is not a discovery report.
